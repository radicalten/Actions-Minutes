ARM7/ARM9 → Broadway JIT: why games hang, and the fixes

Every symptom you described — NDS white screen, GBA black screen after the logo, low FPS, and the Invalid read from 0x00007fff / 0x8000… spam (a Thumb instruction fetch that wandered off into unmapped memory) — is explained by the first five bugs below. Each one alone breaks basically every game. Fixes are ordered by severity; paste the code blocks over the existing functions.

FATAL

1. emitBlockXfer — both conditional branches are inverted

ppc_bc(4, 0, 8) is bge +8: it skips the following b when the helper result is ≥ 0 — which lands in the fail stub (reload + EXIT_FALLBACK at curPC). The runner then re-runs the same LDM/STM in the interpreter, so every LDM/STM executes twice: ldmfd sp!, {r4-r11, pc} pops once in the helper, then pops garbage from SP+N. The second check (cmpi 1; bne +8; b) is inverted the same way, so a loaded PC is thrown away in favour of curPC+4. Since FRAME_PC already holds the right value in both cases, just always use the dynamic exit.

FATAL

2. emitT_pushPop — pop {…, pc} returns to the next instruction

Same inverted bne +8 / b pattern: when the helper reports "PC was popped" (result == 1) the code jumps past the dynamic exit and commits curPC + 2. Every Thumb function return falls through into whatever follows — this is exactly what produces a Thumb fetch stream marching through unmapped memory (0x8000, 0x8002, 0x8004…).

FATAL

3. emitT_addSpPc — sub sp, #imm becomes add sp, #imm

Thumb format 13 is 1011 0000 S imm7: bits 11-8 are 0000 for both add and sub; the sign is bit 7. The code tests (op >> 8) & 0xF == 1 for sub, which never happens, so 0xB080|imm takes the add path.

FATAL

4. emitT_hiReg — add/mov pc must not interwork; blx rX must set LR

Thumb add pc, rX is how GCC implements switch jump tables; the computed address has bit 0 clear. Routing it through emitBX_SCR0 clears the T bit and the CPU starts decoding Thumb code as ARM. Likewise mov pc, rX stays in Thumb on ARMv4/v5. Also, bit 7 of the BX encoding means BLX on ARM9 (very common in DS code); the current code treats it as BX and never writes LR, so the callee returns to a stale address.

FATAL

5. runCpu — never JIT the BIOS region while an HLE BIOS is installed

With interp.bios != nullptr the interpreter's runOpcode() intercepts special addresses inside the BIOS range (IRQ entry / the magic IRQ-return address handled by handleHleIrq / finishHleIrq). validPC() allows pc < 0x8000 and pc >= 0xFFFF0000, so the JIT happily fetches zeros from a non-existent BIOS and compiles them. The IRQ handler's bx lr then lands in JIT'd garbage instead of finishHleIrq(), CPSR/SPSR are never restored, and the game hangs after its first VBlank interrupt. This also removes the per-64-blocks printf, which alone costs you most of your FPS.

HIGH

6. Flag code — V is never set, temporaries get clobbered, TST/TEQ trash the shifter carry

  • rlwinm TE,TE,3,3,3 rotates bit 31 left by 3 → bit 2, then masks bit 28 → result is always 0. Needs sh = 29.
  • setNZ and setC_xer use TA (r3) as scratch, but every caller then passes TA to setV_* as an operand (emitDP reloads opB into TA; Thumb CMP/ADD/SUB/NEG use TA). Move flag scratch to r12, which never holds an operand.
  • In emitDP the test result register is TC — the same register the shifter uses for carry-out — so TST/TEQ with a shifted operand set C from the result's bit 0. Use r10 for test results.
  • Reject the S=0 “test” opcodes in emitDP (that space is MRS/MSR/BX/CLZ/QADD/SMUL*).
HIGH

7. Right-shift carry-out is rotated the wrong direction

For LSR/ASR/ROR #i the carry is bit i-1 of the source. rlwinm TC, s, i, 31, 31 rotates left by i, moving bit i-1 to bit 2i-1, not to bit 0. You need a left rotate of (32 - (i-1)) & 31. (LSL was already correct.)

HIGH

8. Late return false after code was already emitted

emitLSExtra returns false after emitCondSkip() for LDRD/STRD and for Rm == 15. The half-emitted code stays in the buffer and the cond-skip bc is left with offset 0 — a branch to itself. Any conditional LDRD/STRD whose condition is false hangs the Wii. Fix both the specific function and make compile() roll back the cursor so this class of bug can't recur.

MEDIUM

9. dispARM — the MRS/MSR test swallows BX, CLZ, QADD, SWP, SMUL*

(op & 0x0F900000) == 0x01000000 matches the whole misc space, including BX (0x012FFF10). Every BX therefore falls back and emitBX is dead code (which also hid any bugs in it). Tighten the mask to require bits 7-4 == 0 — but only together with the isTest && !s guard from #6, otherwise CLZ/QADD would flow into emitDP.

MEDIUM

10. Helper semantics that diverge from the interpreter

  • PC alignment: emitBX_SCR0 only clears bit 0; align in JitHelp_commit according to the T bit.
  • ARM7 never interworks on LDM/POP pc (ARMv4T). Only the ARM9 does.
  • Unaligned LDR rotates the loaded word on ARM; NooDS does this in ldrOf. Add a dedicated helper for single-word loads.
  • Thumb LSL/LSR/ASR/ROR by register update C; the JIT doesn't. Fall back until implemented.
PERF / SAFETY

11. Block cache is not tagged by CPU; ARM9:ARM7 run at 1:1

Blocks bake in ctx.interp, cpuIdx and arm7, but the cache key is only the PC. If ARM7 and ARM9 ever run code at the same address the wrong core's block executes. Also run the ARM9 twice per ARM7 step so the timing ratio is at least in the right ballpark.

Two things to verify on your side

  1. getActualPC() after an interpreter step. The whole runner assumes that after jitRunOpcode() executes the instruction at A, getActualPC() returns A+4 (ARM) / A+2 (Thumb). In stock NooDS, flushPipeline() leaves r15 = target + 4 and runOpcode() bumps it to +8 before executing, so between instructions r15 - 8 points at the instruction that was just executed — that would make every FALLBACK instruction run twice. Add a one-off check: 
    uint32_t a = interp.getActualPC(); interp.jitRunOpcode();
if (interp.getActualPC() == a) printf("BUG: PC did not advance after interpreter step\n");
    (use a plain ALU instruction, not a branch). If it fires, compute the next PC from the interpreter's pipeline position instead of r15 - 8.
  2. Keep BLK_ARMS = 1 until a game boots, then raise it. Once multi-instruction blocks are on, remember that a mid-block setPC() is no longer sufficient for FALLBACK: you also need the guest PC of the failing instruction, which you already pass as curPC — so that part is fine.

Suggested order of work

  1. Apply #1, #2, #3, #4 (they're the ones producing the hangs and the 0x8000 fetch stream).
  2. Apply #5 and remove the trace printf — FPS should jump immediately.
  3. Apply #6/#7 together (the two flag bugs currently cancel each other out; fixing only the rotate exposes the clobber).
  4. Apply #8/#9/#10/#11, then run the getActualPC() check above.
  5. Only then raise BLK_ARMS.
