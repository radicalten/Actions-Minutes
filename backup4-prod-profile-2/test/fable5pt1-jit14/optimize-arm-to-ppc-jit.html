ARM9/ARM7 → Broadway (PPC750CL) dynamic recompiler

NooDS-Wii JIT — Performance Audit & Fix Plan

Games boot and run, so correctness of the emitted code is mostly good. The low FPS comes from per-block overhead that dwarfs the work done per block, a code cache that thrashes, and C helper calls on the hottest paths (conditions, memory, flags). Below is where the cycles go and, in priority order, what to change — with drop-in PPC encoders where it matters.

TL;DR — the five things holding FPS down

Biggest

Every block pays ~300–400 host cycles of fixed overhead

Prologue saves r14–r31 (18 stores), JitHelp_syncFrom C call (15 double-indirect loads + null checks), then on exit emitSpill (16 stores) + JitHelp_commit (15 pointer stores + setPC() → flushPipeline() = emulated fetch), then a 22-instruction epilogue, then runCpu() → compile() hash lookup → executeBlock_asm again. With BLK_ARMS=8 and blocks ending at every branch, average block length is ~4–6 instructions, so overhead alone is ≈ 60–80 host cycles per guest instruction. The interpreter costs about that much in total.

Biggest

The 2 MB code buffer holds ~1,500 blocks → constant flushJitCache()

A typical block emits 300–400 PPC words (prologue 29 + sync ≈55 + per-insn 10–30 + one full 50-word commit/epilogue copy per exit, two for conditional branches). That is 1.2–1.6 KB per block, so 2 MB is exhausted after ~1,500 blocks. A DS game's hot set across two CPUs is 5k–20k block starts. If your STATUS line's gen= climbs every few seconds, you are recompiling in a loop. The direct-mapped 4096-entry cache also leaks evicted blocks' code until the next flush.

Large

A C function call per conditional instruction and per memory access

emitCondSkip calls JitHelp_testCond for every predicated ARM instruction (≈30–50 cycles, trashes r3–r12). One mtcrf 0x80,r29 plus a bc does it in 2–4 instructions. Every LDR/STR goes through memory.read() via a helper with frame scratch spills; a 10-instruction inline page-map fast path with lwbrx/stwbrx handles ~95 % of accesses.

Large

Flags are always computed; in Thumb they are almost always dead

Every Thumb ALU op sets NZ(CV) — 4 to 15 extra PPC instructions each (setNZ alone is 6, including mfcr, which is slow on the 750). A one-pass liveness scan over the block removes most of them. PUSH/POP (every function!) currently spill all 16 registers, call C, do per-word memory.write(), and reload all 16.

Free win

Logging to SD on the hot path

Your log shows the same [EXC] vector=08 pc=02000086 line dozens of times in a short window: the game busy-waits with swi 3 (WaitByLoop). If DebugLog writes/flushes to FAT on each call, that is a multi-millisecond SD write per SWI. Buffer logs in RAM, rate-limit the [EXC] line (or log only the first N per vector) and flush on exit. Check this one first — it can single-handedly halve FPS.

Fix plan, in order of payoff ÷ effort

P0 = an afternoon each, no architectural change. P1 = emitter work. P2 = the structural change that actually gets you to full speed. Click to expand.

▶P0
Stop refilling the pipeline on every block exit; sync registers inline
Removes one C call, the emulated fetch in flushPipeline(), and ~30 checks per block.

JitHelp_commit calls interp->setPC(pc), which refills the pipeline through the memory map even though the next thing that runs is almost always another JIT block that never reads the pipeline. Only the interpreter needs it. Keep *registers[15] = pc+8 (ARM) / pc+4 (Thumb), because getActualPC(), exception() and interrupt() derive LR from it; refill lazily.

The isReady()/null checks in JitHelp_syncFrom are redundant: runCpu() already refuses to compile before isReady().

▶P0
One shared exit stub instead of a 50-word spill/call/epilogue copy per exit
Halves emitted code size (conditional branches emit two exits today) → 2× more blocks fit before a flush.

Emit the spill + commit call + epilogue once at JIT init into the code buffer (it depends only on the frame layout). Blocks exit with li TE,pc ; li TF,reason ; b exitStub. The PPC b reaches ±32 MB, so any buffer up to 32 MB works. Likewise, move the prologue + register sync into executeBlock_asm (one copy) and have it bctr into the block body.

▶P0
Longer blocks: keep compiling after a not-taken conditional branch; raise BLK_ARMS
Loop bodies like cmp ; beq exit ; … stop being split at the exit check.

Today a conditional B/BX/LDM-pc/POP-pc/Thumb Bcc emits a taken exit and a not-taken exit and ends the block. Only the taken path needs to leave; the fall-through can continue in the same block. Then raise BLK_ARMS to 32–64 and BLK_WDS/BLK_MARGIN accordingly. (melonDS's JIT defaults to 32-instruction blocks and interleaves ARM9/ARM7 per block — games tolerate it.)

▶P0
Move the code buffer to MEM2 and make it 16–32 MB; drop the MEM1 address checks
Cache flushes become rare instead of continuous.

Code executes fine from cached MEM2 (0x90000000–0x93FFFFFF); Wii64/Not64 keep their recompiled code there. emit_li32 already encodes any 32-bit address, so the a<0x80000000||a>=0x81800000 guard in Ctx::call() and the MEM1 range test in initJit() are just restrictions. You already have Noods_MEM2_Alloc. Keep DCFlushRange + ICInvalidateRange after each compile (they work on MEM2 too).

While there, replace the direct-mapped cache[4096] with a lookup that does not evict: a two-level table blockTable[cpu][pc>>12] → array of (pc & 0xFFF) >> 1 pointers, allocated on first use per page. Lookup is two loads, invalidation is "free the page's array", and it is what the P2 dispatcher wants anyway. Use key = pc | thumb as the block identity (ARM PCs are 4-aligned, Thumb 2-aligned).

▶P0
Compile the four hot fallbacks: mov lr,pc, blx #imm, ldr pc,[…], swi
Each one currently costs exit + interpreter + re-entry, on every call/return/IRQ.

Drop the placeholder oris line in (2) — it is only there to show where the T-bit set goes; ori RCPSR,RCPSR,0x20 is the real instruction.

▶P1
Inline condition codes with mtcrf — replaces JitHelp_testCond
2–4 instructions instead of a C call. ARM's NZCV are the top nibble of CPSR, which is exactly one CR field.

mtcrf 0x80,r29 copies CPSR bits 31..28 into CR0, so cr0.LT=N, cr0.GT=Z, cr0.EQ=C, cr0.SO=V. Simple conditions are one bc; compound ones need one or two CR-logical ops into cr1. The branch is taken when the condition is false (skip the instruction).

Same trick for Thumb Bcc. Once flags live in CR0 you can also cheapen setNZ: use record-form ops (and., add., subfc. — set rc=true in Xf/XOf), then mfcr TS ; rlwinm RCPSR,RCPSR,0,2,31 ; rlwimi RCPSR,TS,0,0,0 ; rlwimi RCPSR,TS,1,1,1 — 4 instructions, no cmpi. Better still: don't compute them at all (next item).

▶P1
Dead-flag elimination (one forward scan per block)
Removes most setNZ/setC/setV sequences — in Thumb, the majority of all emitted instructions.

Pre-decode the block's opcodes into an array (you already read them one at a time; read them all first). For each flag-setting instruction compute which of N/Z/C/V is read before being overwritten by a later unconditional writer in the same block. Anything unknown at block end is live. Pass the live mask to the emitters and skip the dead updates.

Conservative by construction: conditional writers never count as kills, block-ending instructions stop the scan, and a fallback instruction (unknown to the JIT) should be treated as reading everything.

▶P1
Inline memory fast path through the 4 KB page map (lwbrx/stwbrx)
10 instructions for RAM hits; the helper only for I/O, unmapped pages, misaligned words and pages containing compiled code.

Your Memory already maintains 4 KB page pointer tables (updateMap9/updateMap7). Give the JIT its own copies: jitReadMap[cpu] = the read map plus the ARM9 TCM regions (the stack lives in DTCM — sp=027C3B2C in your log — so it must be in the fast path), and jitWriteMap[cpu] = the write map with every page that contains a compiled block set to null for both CPUs. Stores to code pages then take the slow path, which is where invalidateJitPage() lives — no per-store check needed. Rebuild the JIT maps whenever the memory map or TCM config changes (hook updateMap* and the CP15 TCM writes). Guest data is little-endian in memory, hence the byte-reversed loads. Keep a dedicated register for the map base (e.g. r31; the prologue loads it once).

If memory.read() checks ITCM/DTCM before the map (as upstream NooDS does), reproduce that ordering when building jitReadMap, or the JIT will read main RAM where the CPU would read DTCM.

▶P1
Inline PUSH/POP, LDM/STM, and register-specified shifts
PUSH/POP is 16 spills + C call + per-word memory.write() + 16 reloads today, on every function entry/exit.
  • PUSH/POP/LDM/STM without PC: with the page map in a register, emit one page lookup + one "fits in page" check, then a straight run of stwbrx/lwbrx from/to the mapped ARM registers. No spill/reload. Lists with PC: do the loads inline, then go through emitBX_target. Fall back to the helper only on the slow path.
  • LSL/LSR/ASR/ROR by register (Thumb ALU 2/3/4/7, ARM *Llr forms): emitShiftCall spills CPSR and calls C. Inline: rlwinm amt,amt,0,24,31 (low 8 bits), cmplwi amt,32; for amounts under 32 use slw/srw/sraw/rlwnm, and handle 32 / over-32 on a short branch. Only compute the carry if it is live (dead-flag mask).
  • Thumb ldr rd,[pc,#imm]: address is a compile-time constant; use the fast path (or, if the page is ROM/RAM that cannot change, read the constant at compile time and emit li — but then the block must be invalidated if that page is written, which your page tracking already gives you if you register the literal's page).
▶P2
Dispatcher loop + block linking + cycle down-counter (the change that reaches full speed)
Registers stay in r14–r29 across blocks; block-to-block transfer costs a b or a 6-instruction hash lookup instead of 300+ cycles.

Model. C calls jitEnter(cpu, budget) once per time-slice. One prologue saves non-volatiles, loads ARM regs, puts the map base in r31 and the cycle budget in r30, then jumps to the first block. Blocks never return to C on their own; they jump to one another. The generated code returns to C only when: the down-counter goes ≤ 0, a fallback/SWI/halt/CP15 instruction is reached, or a lookup misses and compilation is needed. The runner then does globalCycles += used and runs due tasks.

Details that matter.

  • Patching a b: write the word, DCFlushRange/ICInvalidateRange the 32-byte line. When a block is invalidated, unlink everything pointing at it (keep a small back-reference list per block) by restoring b resolve_T.
  • Two CPUs: give each a slice of ~128–512 ARM9 cycles (a setting), alternate, and clamp the slice to the next scheduler event. This is the same granularity melonDS's JIT uses; IPC-heavy titles may need the smaller value.
  • Interrupts: ARM9_INTERRUPT/ARM7_INTERRUPT are scheduler tasks, so they run between slices — set the pending IRQ to also zero r30's budget in the runner so latency stays bounded (e.g. interrupt() sets a flag the runner checks before each slice; end the current slice early by exposing a "cycles left" location the C side can clear).
  • Keep EXIT_FALLBACK semantics: the exit stub commits at the faulting PC, C runs jitRunOpcode() once, then re-enters.
  • Halt (swi 6, mcr p15,0,rX,c7,c0,4): fallback → interpreter sets halted → updateRun() → your runner already exits on running==0.

Once this is in, P0.1/P0.2 become moot (there is one prologue/epilogue in the whole system) — but doing them first is still worth it: they are small, they let you measure, and every piece of emitted code carries over.

Correctness nits found while reading

None of these explain the FPS, but a few will bite as coverage grows. The flag/carry logic (subfc CA = NOT borrow, primeCarry via addic r0,TS,-1, V from xor of operands) checked out.

bug
emitMrsMsr returns false after emitting code. The rm==15 check for the register form happens after emitCondSkip; the dangling cond-test is harmless but wasted. Test rm before emitting.
bug
Direct-mapped cache eviction leaks code. compile() invalidates the colliding slot but its code stays in codeBuf until the next full flush; ARM9 and ARM7 blocks collide with each other via cpu<<11. Symptom: gen= increments faster than the working set justifies. Fixed by the page-table lookup in P0.4.
bug
[EXC] log prints the wrong PC in Thumb (02000086 for the SWI at 02000088) — it uses r15−4 regardless of mode. Cosmetic, but it will mislead you when debugging Thumb faults.
perf
executeBlock_asm saves r30/r31 that the block prologue saves again; and runCpu() calls compile() (validPC + hash + 5 compares) on every block execution even when it is a hit. Split into lookup() and compile().
perf
runDueTasks erases from the front of a vector (O(n) shift per event; fine now with ~10 events, keep an eye on it). fbLogOnce does a linear scan of up to 512 entries on every fallback — cheap relative to the fallback itself, but it is on the hot path when a hot fallback exists.
note
Timing: armCycles/thumbCycles are constants while the interpreter charges real memory waitstates. Expect games to run slightly "fast" in emulated time compared with the interpreter; if a title becomes unstable after longer blocks, that is the first knob to look at (charge 1 extra for loads from main RAM, 3–4 for ROM/VRAM).
note
CPSR writes from generated code bypass setCpsr(). Correct today because the JIT only touches NZCV and T. Keep it that way: mode/I/F changes must stay on the interpreter (they are — emitMrsMsr only accepts the flags field).

Measure before and after each step

Add these counters to the STATUS line

  • gen — flushes per minute. Anything above ~0 in steady state means the code cache is too small or leaking.
  • Guest instructions executed by JIT vs by interpreter (sum b->insnCount per execution vs interpStep calls). Target: over 98 % JIT.
  • Blocks executed per second and average insnCount per executed block. Target: 20+.
  • Top fallback PCs by count, not just first occurrence — a fallback in a hot loop matters 1000× more than one at boot.
  • Time split with PPCGetTickCount(): JIT blocks / interpreter / scheduler tasks (GPU scanlines, SPU) / frame end. If GPU tasks are already 50 % of the frame, no CPU work will double FPS — test with a 2D-only title to isolate CPU cost.

Suggested order

  1. Log buffering + rate limits (minutes). Re-measure.
  2. P0.1 + P0.2 + P0.3 + P0.4 together — they are all "less code per block, fewer C calls, bigger buffer". Expect blocks/s to drop and insns/block to climb 3–5×.
  3. P0.5 hot fallbacks — watch the fallback counters go to ~0 for ARM7.
  4. P1.1 conditions, P1.2 dead flags, P1.3 memory, P1.4 PUSH/POP — each is independently measurable.
  5. P2 dispatcher — do it last, with the emitters already proven; it is mostly runner/stub work by then.

Rule of thumb for Broadway: a taken bctrl to a C helper plus its prologue costs about as much as 25–40 straight-line integer instructions. Every helper you remove from a hot path is worth more than any micro-optimisation inside one.
